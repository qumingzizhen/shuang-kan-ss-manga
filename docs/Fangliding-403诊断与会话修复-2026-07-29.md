# Fangliding 公开访问 403 诊断与会话配置修复

> 日期：2026-07-29

## 现象

最新搜索任务 `ca4797dc-c859-4bbe-b9b2-e662fa8ae158` 在 2026-07-29 22:53 完成：18comic 与 E-Hentai 正常返回并合并 65 条结果，Fangliding 单源失败。桥接错误为 `access_blocked`，目标地址是：

```text
https://ex.fangliding.eu.org/?f_search=female%3Afutanari&f_cats=0&page=0
```

前一天的同类三源任务仍能获得 90 条合并结果，因此这不是固定的查询映射或解析错误。

## 诊断结论

1. 从本机直接访问 Fangliding 首页返回 HTTP 403。
2. 直接访问同一搜索 URL 返回 HTTP 403。
3. 使用现代浏览器 User-Agent、`Sec-Fetch-*` 和 Client Hint 等完整导航请求头仍返回 HTTP 403。
4. 反向代理没有参与以上直接请求，因此本次阻断不是 Next.js Rewrite 造成的。
5. Fangliding 桥接器本来支持 `FANGLIDING_COOKIE_FILE` 和 `FANGLIDING_HEADERS_FILE`，但 `config/source-adapters.json` 没有声明认证能力，控制台无法提供配置入口。这是项目内部的实际缺口。

公开检索信息仍指向同一个域名，没有发现可验证的新官方镜像域名；第三方状态检查对站点是否可用的结论不一致。项目不会猜测域名，也不会用 E-Hentai 的结果冒充 Fangliding。

## 项目修复

- Fangliding 适配器版本由 `0.4.0` 升级为 `0.4.1`。
- 在统一源站注册表中声明 Cookie/请求头认证能力；控制台继续复用通用 `SourceAuthPanel`，没有新增 Fangliding 专用界面或链路。
- 保存内容仅通过通用原子私密写入器写入被 Git 忽略的 `.data/source-auth/fangliding.cookies.txt` 和 `.data/source-auth/fangliding.headers.txt`，中断时不会留下半写文件。
- 搜索页全部被拦截时保留 `HttpStatusError` 类型，桥接错误稳定输出 `access_blocked`，不再依赖错误文案中的关键词推断类型。
- 离线测试同时覆盖分页规则、认证注册与阻断错误契约。
- 隔离开发 API 的端到端测试已经验证 `/v1/sources` 会公开 Fangliding 的 Cookie/请求头字段，`PUT/DELETE /v1/source-auth/fangliding` 能正确保存和清除虚构会话；测试目录随后已删除。

## 使用方法

修改生效后需重新加载配置：

```powershell
cd "<项目目录>"
.\scripts\dev.ps1 -Fresh
```

然后：

1. 来源选择 `Fangliding`。
2. 展开“Fangliding 浏览器会话”。
3. 如果你本人在浏览器中可以正常打开该站，把该浏览器会话中有权使用的 Cookie 或请求头粘贴到面板并保存。
4. 重新运行 Fangliding 搜索。

不要把 Cookie、Cloudflare clearance、账号信息或私有请求头提交到 GitHub。

如果普通浏览器本身也得到 403，则当前是站点端或网络侧访问限制。项目会继续保留其他来源结果并明确标记 Fangliding 暂时不可用，但不会破解验证码、绕过 Cloudflare、封禁或访问控制。此时只能等待站点恢复，或由用户提供自己有权使用的正常浏览器会话。
