# 搜索结果信息分层与跨来源排序说明

> 完成日期：2026-07-26
> 适用范围：Next.js 搜索结果界面、Node.js 开发 API、Python 来源桥接、Rust 搜索结果契约。
> 兼容原则：原有任务入口、搜索入参、下载和阅读流程保持不变；新增字段均为可选字段。

## 1. 完成结果

本轮将搜索结果从“封面卡片直接堆放操作”调整为两级信息结构：

- 一级结果采用 E-Hentai 风格的自适应封面网格，宽屏显示五列并随可用宽度降为四、三、两列；
- 一级显示漫画名称、来源、分类、上传人和上传时间；
- 来源没有返回某项元数据时不伪造、不显示空占位；
- 单条在线阅读、下载、来源页面和完整 Tag 移入二级详情；
- 二级详情首次打开时按需读取图库元数据，后续五分钟内复用查询缓存；
- 默认按上传时间由近到远排列；
- 没有上传时间的结果按来源轮转，避免单个来源连续占满首屏；
- 下滑加载下一页后重新对完整结果集合排序。

原有批量勾选、全选、清空和批量下载仍保留，未改变用户已有的批处理流程。

## 2. 数据链路

```mermaid
flowchart LR
    S["来源搜索页或 API"] --> P["来源轻量元数据解析"]
    P --> N["统一可选字段规范化"]
    N --> D["来源 + 链接去重"]
    D --> O["已知时间降序"]
    O --> R["无时间结果按来源轮转"]
    R --> L["一级封面网格"]
    L -->|打开详情| Q["按需图库详情查询"]
    Q --> C["TanStack Query 五分钟缓存"]
    C --> T["二级详情：Tag / 阅读 / 下载"]
```

搜索阶段不会为每条结果额外请求图库详情。E-Hentai 的分类、上传人、时间和行内 Tag 从搜索结果所在结构块中轻量解析；18comic 优先读取 JM API 已返回的兼容字段，网页回退仅在页面确实存在对应元素时保留数据。

## 3. 兼容数据契约

`TaskSearchResult` 原有字段保持不变，新增三个可选字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `uploader` | `string \| null` | 上传人；来源未提供时为空 |
| `uploaded_at` | `string \| null` | 可解析的上传时间；开发 API 规范化为 ISO 时间 |
| `category` | `string \| null` | `Doujinshi`、`Manga`、`Game CG` 等粗分类 |

二级详情响应沿用全部搜索结果字段，并可额外返回可选的 `page_count`。新增接口：

```http
POST /v1/search-result-details
Content-Type: application/json
```

请求仍使用 `source_id` 和 `gallery_url`，服务端校验来源存在、链接非空后调用原有 `gallery` 桥接命令。该接口是新增入口，不改变 `/v1/tasks`、`/v1/reader` 或下载任务接口。

## 4. 排序规则与复杂度

默认排序分为两组：

1. 可解析上传时间的结果：严格按时间降序，时间相同时保持原顺序；
2. 缺失或无法解析时间的结果：排在有时间结果之后，并按来源队列轮转。

例如原始无时间序列：

```text
A1, A2, B1, B2, C1
```

会变为：

```text
A1, B1, C1, A2, B2
```

主排序复杂度为 $O(n \log n)$，来源轮转为 $O(n)$；额外空间为 $O(n)$。每次加载更多后对合并集合重新排序，避免新页结果永久堆在末尾。

网页端同时提供“最新上传、最早上传、名称”三个排序选项。服务端默认顺序和网页默认顺序一致；网页再次排序是兼容旧任务快照及其它后端实现的防御措施。

## 5. 代码结构优化

优化前，仪表盘组件内联承担结果卡片、Tag、阅读、下载和选择状态渲染：

```tsx
<InfiniteSearchResults
  renderResult={(result) => (
    <div>
      {/* 封面、Tag、阅读、下载全部混在任务详情 */}
    </div>
  )}
/>
```

优化后，仪表盘只传递业务回调：

```tsx
<SearchResultsView
  results={detailSearchResults}
  onRead={openRemoteReader}
  onDownload={downloadSearchResult}
/>
```

职责拆分如下：

| 模块 | 职责 |
| --- | --- |
| `search-result-model.ts` | 结果键、时间解析、分类中文名、稳定排序 |
| `search-results-view.tsx` | 一级封面网格、排序控件、二级详情和可访问性 |
| `search-results.tsx` | 无限加载与封面重试状态机 |
| `search-result-metadata.py` | 来源搜索结构块的轻量元数据提取 |
| `search-pipeline.mjs` | 规范化、去重、默认排序和来源轮转 |

二级详情最初的手动缓存、请求序号、loading 和 error 状态已删除，统一接入项目现有 TanStack Query。这样没有形成第二套请求缓存链路。

## 6. 性能复测

同一台机器使用 `scripts/measure_baseline.ps1` 测量。当前样本数为 12，HTTP 数据用于发现明显回退，不用于宣称远端来源抓取速度提升。

| 指标 | 上一轮 | 当前 | 变化 |
| --- | ---: | ---: | ---: |
| 前端单元测试墙钟时间 | 3,210.9 ms（21 项） | 2,860.0 ms（26 项） | -10.93% |
| Next.js 正式构建 | 9,129.4 ms | 8,330.1 ms | -8.76% |
| standalone 产物 | 16,370,915 B | 16,388,851 B | +0.11% |
| static 产物 | 957,835 B | 979,632 B | +2.28% |
| API 健康检查 p95 | 9.97 ms | 12.29 ms | +23.27% |
| 开发态首页 p95 | 96.95 ms | 99.78 ms | +2.92% |

API p95 的绝对值仍低于 20 ms 门槛；本轮样本数较小，2.32 ms 差异属于继续观察项。一级列表只使用搜索响应中的轻量元数据，完整图库详情只在用户打开二级详情时请求，因此搜索首屏没有引入按结果数量线性增长的网络请求。

## 8. 已知边界

- 来源不提供上传人、分类或时间时，界面不会猜测；
- 各来源时间精度不同，只有日期的结果只能按日期粒度排序；
- 某些站点改版后可能暂时无法从搜索页提取元数据，但基础标题、链接、封面和二级详情仍保持兼容；
- 二级详情遵守来源登录、验证码、限流和访问控制，不尝试绕过。
