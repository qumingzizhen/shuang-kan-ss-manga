# 长期大规模优化计划（2026-08-05）

> 时间跨度：约 6 个月，分 6 个阶段滚动执行。
> 适用范围：前端阅读器、开发 API、Python 源站桥接、Rust 服务、缓存与部署。
> 核心约束：契约优先、源站礼貌与合规红线、实测数据驱动、一次提交只解决一个问题。

## 1. 目标

把「能用」提升到「快、稳、可观测、可规模化」：

1. 阅读体验：首图与翻页延迟降到源站物理极限，缓存命中路径接近零延迟；
2. 抓取吞吐：在**不增加源站封禁/限流风险**的前提下，让下载与阅读预取吞吐提升 1.5–2 倍；
3. 代码可演进：拆掉 3963 行 `server.mjs` 与 4759 行 `dashboard.tsx` 两块巨石，
   让后续每个优化都有独立、可测试的模块；
4. 可观测：任何一次慢请求都能定位到「源站 RTT / Python 启动 / 缓存 / 解码 / 渲染」哪一环；
5. 规模化：从单机本地走向多实例/公网部署时，缓存与搜索不成为瓶颈。

## 2. 现状基线（2026-08-05）

已完成（本轮）：

- 建会话只抓首页索引、首图后台预热、页列表惰性补全 + 后台渐进扩展；
- display/blur WebP 变体、老缓存回填、精确尺寸占位、blur-up 渐显；
- 整本受控预取、镜像源故障切换、ETag/304、TTL/容量缓存治理；
- Service Worker 浏览器缓存、滚动稳定性修复（只增不减堆栈）；
- 实测：Fangliding 建会话 1.8–2.1s、首图 4.2–4.8s（源站 RTT 主导）、缓存图片 6ms、
  重复打开 3ms、深跳单索引页 ~1.7s、800 页阅读器 DOM 堆内存 ~12MB。

关键规模与瓶颈：

| 对象 | 规模 | 影响 |
| --- | --- | --- |
| `services/dev-api/server.mjs` | 3963 行 | 路由、缓存、调度、桥接、任务全部耦合，难以独立演进 |
| `apps/web/src/components/dashboard.tsx` | 4759 行 | 阅读器、任务、搜索、库全部耦合，任何重渲染都扫全树 |
| 每次 `runSourceBridge` | spawn 一个新 Python 进程 | 单次 100–400ms 启动开销，且无法复用 HTTP 连接 |
| `page-cache` 目录 | 每请求全目录 stat | 会话文件 >200 后查找开销线性增长（M2 已标注） |
| `characters.source.json` + 翻译文件 | 51MB + 50MB | 标签翻译加载与内存占用大 |
| `check_performance_baseline.mjs` | 仅覆盖搜索合并/排序 | 阅读器与桥接没有纳入 CI 性能预算 |

## 3. 优化领域与重点项目

### A. 可观测与性能基线（先建度量，再动手）

- 统一计时与上下文日志：桥接调用耗时、Python 启动耗时、缓存命中率、变体生成耗时、
  解码/首绘时间，按源站聚合，输出结构化 JSON 日志；
- 阅读器基准（`scripts/benchmark_reader_dom.mjs` 已入库）纳入定期回归：DOM 数、
  内存、帧间隔、跳顶事件、首图延迟；
- 性能预算表进 CI：新增优化必须附前后对比数据（工程规则硬性要求）；
- 新增 `/v1/diagnostics` 扩展：缓存命中、预取进度、源站延迟、队列积压。

### B. 阅读器与前端

- 把阅读器从 `dashboard.tsx` 抽成独立模块（容器/展示组件、自定义 Hook、请求层），
  与已有的 task-drawer、remote-reader-history 重构同模式推进；
- 渲染预算：滚动模式帧预算（真实滚轮下 P95 帧间隔 < 33ms）、首图预算、
  800 页内存预算 < 50MB；数据不达标时再评估虚拟化（当前数据不支持）；
- 图片管线：显示版 WebP 已落地；后续加 AVIF 选项、按带宽/设备出 `srcset`、
  渐进式 JPEG 选项、`createImageBitmap` worker 预解码；
- 交互细节：跳页精确滚动、滚动位置恢复精度、键盘/触控板手感。

### C. 后端与 API

- `server.mjs` 按域拆包：source-registry / reader / cache / task / state / bridge，
  保持对外路由与响应结构不变（纯结构性重构，独立提交）；
- 缓存层级化：内存 LRU → 磁盘 page-cache（目录扫描改 SQLite 索引）→ SW；
  索引记录访问时间、尺寸、变体，供 TTL/容量驱逐直接查询；
- JSON 响应优化：列表接口 ETag/304、字段裁剪、Brotli（公网部署时）；
- 并发调度：async-pool 参数化，下载配额与阅读预取共用同一套速率账本，
  避免整本预取与用户请求互相饿死；
- 任务/会话查询加索引（迁移到 Postgres 后），阅读会话按 `updated_at` 分页。

### D. 源站适配与抓取（吞吐提升的主战场）

- **常驻桥接进程**：把「每次调用 spawn Python」改为按源常驻一个 worker 进程，
  复用 HTTP/2 连接与会话；预计每次调用节省 100–400ms，且降低整体请求数；
  需要进程协议（stdin/stdout JSON-RPC）、崩溃重启、超时与优雅退出；
- 自适应礼貌：记录每源延迟、429/403 频次、成功率，动态调整预取节奏与并发，
  但**永远不绕过限速/验证码边界**（红线）；
- 多源演进：镜像故障切换已落地；后续按延迟历史做「慢源降级」与内容寻址全局缓存
  （同一图库多镜像共享磁盘缓存）；
- 下载任务：分片进度、断点续传、失败页面结构化重试计划（已有 retry-plan，增强）。

### E. 数据与存储

- 标签字典：51MB+50MB JSON 改懒加载/裁剪/二进制（如 sqlite fts 或按需读取），
  目标内存占用 < 20MB；
- SQLite → PostgreSQL：完成 roadmap 中未完成的迁移验证，任务/会话/书签全部入库，
  加索引；文件库扫描保留本地 watch；
- 搜索：dev-api 内存 pipeline 与 Meilisearch（compose 已有）试点，按检索量决策；
- 导出链路：CBZ/PDF 大文件流式生成，避免整包进内存。

### F. 部署与规模化

- 图片走 CDN/边缘缓存（Cloudflare 等）时使用签名 URL，仅缓存 display/blur 变体；
- 多实例部署：共享 page-cache 需 Redis 索引 + 对象存储；会话状态必须可共享
  （当前 SQLite 单机假设要先解除）；
- HTTP/3、连接复用、Brotli 静态资源；
- PWA/离线：SW 已有，补齐离线启动清单与更新策略；
- 一键部署（docker-compose 已有雏形）与 nginx 模板（已有）对齐新缓存头。

## 4. 阶段路线图

| 阶段 | 周期 | 主题 | 关键交付 | 验收 |
| --- | --- | --- | --- | --- |
| P0 | 第 1–2 周 | 观测与基线 | 结构化计时日志、阅读器基准入回归、KPI 台账 | 任何慢请求可定位到环节 |
| P1 | 第 3–6 周 | 阅读器与缓存纵深 | dashboard 阅读器拆包、page-cache 索引化、srcset/AVIF 试点 | 滚动 P95 帧间隔达标；缓存查找不再全目录 stat |
| P2 | 第 7–10 周 | 抓取链路重构 | 常驻桥接进程、自适应礼貌、下载调度共享账本 | 桥接调用开销下降，吞吐提升 1.5–2x，0 新增封禁 |
| P3 | 第 11–14 周 | 后端模块化与持久化 | server.mjs 按域拆包、Postgres 迁移完成、标签字典瘦身 | 全量检查通过且契约不变；内存下降 |
| P4 | 第 15–20 周 | 部署与多实例 | CDN 图片、Redis 共享缓存、HTTP/3、PWA 离线 | 多实例下缓存命中一致；离线可用 |
| P5 | 持续 | 治理与复测 | 每季度复跑基准、技术债台账更新、按数据决定后续取舍 | 基准无回归；债务有偿还记录 |

每个阶段内部按「一个任务一个提交」推进；涉及对外行为的新能力默认关闭或带
env 开关，先灰度再默认。

## 6. 治理机制

- 每项优化先立基准再实施，提交信息附前后数据或指向基准文档；
- `scripts/check.ps1` 只跑确定性的回归；基准类脚本单独定时/按需运行，不拖慢日常检查；
- 技术债台账：本文件作为入口，记录每阶段未完成项与偿还计划；
- 红线重申：不绕过登录/验证码/限速；不破坏对外接口；默认配置保证零配置可运行；
- 回滚策略：每个优化独立提交、独立开关，出问题只回滚对应提交。
