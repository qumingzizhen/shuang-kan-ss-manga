# 跨设备同源反向代理部署指南

> 日期：2026-07-29

> 适用版本：Next.js 16.2.12、Python 开发 API / Rust 生产 API（统一 /v1/ 契约）

## 1. 目标与边界

浏览器只访问前端设备的同一个 Origin。前端设备在服务端把 `/v1/**` 原样转发到后端设备，因此浏览器不会直接看到后端 IP，也不需要后端开放 CORS。

```text
浏览器
  -> http://前端设备:3000/               Next.js 页面
  -> http://前端设备:3000/v1/**          同源 API 请求
       -> http://后端设备:8080/v1/**      服务端反向代理
```

本次没有修改 Python/Rust 业务路由、接口入参、返回结构、前端业务组件、阅读器或 `apps/web/src/lib/api.ts`。Python 开发 API 只增加可选的监听地址；默认仍为 `127.0.0.1`。

## 2. 配置变量

| 变量 | 默认值 | 使用位置 | 说明 |
|---|---|---|---|
| `BACKEND_API_URL` | `http://127.0.0.1:8080` | Next.js / Nginx | 服务端可访问的后端根地址，不要带 `/v1`、查询参数或账号密码 |
| `BACKEND_PROXY_TIMEOUT_MS` | `900000` | Next.js | 外部 Rewrite 超时，默认 15 分钟，兼容 SSE、封面和阅读图片流 |
| `DEV_API_BIND_HOST` | `127.0.0.1` | Python 开发 API | 跨设备开发时设为 `0.0.0.0`；本机开发不配置 |
| `API_BIND` | `0.0.0.0:8080` | Rust API | Rust 生产服务监听地址 |
| `FRONTEND_APP_URL` | `http://127.0.0.1:3000` | Nginx | Nginx 转发页面时使用的 Next.js 地址 |
| `GATEWAY_LISTEN_PORT` | `80` | Nginx | Nginx 对外监听端口 |

`BACKEND_API_URL` 和超时属于服务端配置，不使用 `NEXT_PUBLIC_` 前缀，不会暴露到浏览器包中。配置文件会拒绝非 HTTP(S) URL、URL 内嵌凭据、查询参数、片段和越界超时。

## 3. 方案 A：Next.js 内置 Rewrites（推荐作为当前最小部署）

适合前端设备持续运行 Node/Next.js、不想再部署 Web 服务器的情况。

### 3.1 完整配置

真实配置文件为 `apps/web/next.config.ts`：

```ts
import type { NextConfig } from "next";

import { apiRewrite, backendProxyTimeoutMs } from "./proxy-config";

const nextConfig: NextConfig = {
  output: "standalone",
  reactStrictMode: true,
  env: {
    NEXT_PUBLIC_API_BASE: "",
  },
  experimental: {
    proxyTimeout: backendProxyTimeoutMs,
  },
  async rewrites() {
    return [apiRewrite];
  },
};

export default nextConfig;
```

`apps/web/proxy-config.ts` 负责解析、校验和测试环境变量，最终生成：

```ts
{
  source: "/v1/:path*",
  destination: `${BACKEND_API_URL}/v1/:path*`,
}
```

External Rewrite 不限定 HTTP 方法，会保留 GET、POST、PUT、PATCH、DELETE 的请求方法、请求头、查询参数和请求体；搜索、任务、SSE、封面、阅读图片、源站配置、下载和本地文件库只要位于 `/v1/` 下都会走同一条规则。

### 3.2 本机开发（零额外配置）

```powershell
cd "<项目目录>"
.\scripts\dev.ps1
```

脚本仍会自动选择可用的 API/Web 端口。区别仅在于它把最终 API 地址写给 `BACKEND_API_URL`，浏览器始终请求同源 `/v1/**`。强制重载最新代码仍使用：

```powershell
.\scripts\dev.ps1 -Fresh
```

### 3.3 跨设备部署

假设：

- 后端设备局域网 IP：`192.168.1.20`
- 前端设备局域网 IP：`192.168.1.10`
- API 端口：`8080`
- Web 端口：`3000`

后端设备使用 Rust 生产 API：

```powershell
$env:API_BIND = "0.0.0.0:8080"
# 按项目既有 Rust 生产启动方式启动 services/api
```

后端设备使用 Python 开发 API：

```powershell
cd "<项目目录>"
$env:DEV_API_BIND_HOST = "0.0.0.0"
$env:DEV_API_PORT = "8080"
node .\services\dev-api\server.mjs
```

前端设备在构建前设置后端地址，然后监听局域网接口：

```powershell
cd "<项目目录>"
$env:BACKEND_API_URL = "http://192.168.1.20:8080"
$env:BACKEND_PROXY_TIMEOUT_MS = "900000"
npm --prefix .\apps\web run build
npm --prefix .\apps\web run start -- --hostname 0.0.0.0 --port 3000
```

局域网用户访问 `http://192.168.1.10:3000`。只应在防火墙中允许前端设备访问后端的 8080 端口，不建议把开发 API 直接暴露到公网。

Next.js Rewrites 在构建/服务启动时读取目标地址。修改 `BACKEND_API_URL` 后必须重新构建并重启前端进程，不能只刷新浏览器。

### 3.4 不可达错误的行为

Next.js 内置 External Rewrite 在连接失败或超时时返回标准 HTTP 500 和 `Internal Server Error`。现有前端请求封装本来就支持非 JSON 错误文本，因此会进入统一错误提示，不会表现为 CORS 错误。

纯 `rewrites` 没有可配置的错误体钩子，无法把代理自身的 500 改写成后端同款 `{"error":"..."}` 而又同时满足“只改配置层、不得增加 Route Handler/自定义 Node Server”的约束。需要稳定 JSON 502 时使用下方 Nginx 方案；本项目没有为掩盖这一平台边界而侵入业务 API 层。

## 4. 方案 B：Nginx 同源网关（推荐生产部署）

适合需要标准 JSON 502、TLS、稳定流式转发和运行时切换后端的生产环境。模板位于 `infra/nginx/manga-platform.conf.template`。

### 4.1 完整模板

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen ${GATEWAY_LISTEN_PORT};
    server_name _;
    client_max_body_size 100m;

    location /v1/ {
        proxy_pass ${BACKEND_API_URL};
        proxy_http_version 1.1;
        proxy_set_header Host $proxy_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Port $server_port;
        proxy_request_buffering off;
        proxy_buffering off;
        proxy_cache off;
        add_header X-Accel-Buffering no always;
        proxy_connect_timeout 5s;
        proxy_send_timeout 900s;
        proxy_read_timeout 900s;
        send_timeout 900s;
        proxy_intercept_errors on;
        error_page 502 504 = @backend_unavailable;
    }

    location @backend_unavailable {
        internal;
        default_type application/json;
        add_header Cache-Control "no-store" always;
        return 502 '{"error":"backend API unavailable; check BACKEND_API_URL and network connectivity"}';
    }

    location / {
        proxy_pass ${FRONTEND_APP_URL};
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
    }
}
```

项目中的权威版本是 `infra/nginx/manga-platform.conf.template`；上面的代码省略了模板内的解释性注释，但指令完整一致。

### 4.2 生成配置

Linux 前端设备示例：

```bash
export GATEWAY_LISTEN_PORT=80
export FRONTEND_APP_URL=http://127.0.0.1:3000
export BACKEND_API_URL=http://192.168.1.20:8080

envsubst '${GATEWAY_LISTEN_PORT} ${FRONTEND_APP_URL} ${BACKEND_API_URL}' \
  < infra/nginx/manga-platform.conf.template \
  > /etc/nginx/conf.d/manga-platform.conf

nginx -t
nginx -s reload
```

必须使用上面的“变量白名单”调用 `envsubst`，否则 Nginx 自己的 `$host`、`$remote_addr` 等运行时变量也会被错误替换为空字符串。

Next.js 在 Nginx 后面仍可使用默认同源配置：

```bash
BACKEND_API_URL=http://127.0.0.1:8080 npm --prefix apps/web run build
npm --prefix apps/web run start -- --hostname 127.0.0.1 --port 3000
```

浏览器访问 Nginx 的 80/443 端口。Nginx 将 `/v1/` 直接转发后端，将其他路径转发 Next.js；不会添加任何 CORS 响应头。模板关闭请求/响应缓冲并设置 900 秒流式超时，适配 SSE、下载、封面与阅读图片；连接失败或网关超时会返回：

```json
{"error":"backend API unavailable; check BACKEND_API_URL and network connectivity"}
```

现有前端会读取 `error` 字段并显示该消息。

## 5. 部署验证

### 5.1 基础连通性

先在前端设备直接检查后端：

```powershell
Invoke-RestMethod "http://192.168.1.20:8080/v1/sources"
```

再检查同源代理：

```powershell
Invoke-RestMethod "http://192.168.1.10:3000/v1/sources"
```

Nginx 方案把第二个地址的端口改为 80/443。两次响应的字段结构应一致。

### 5.2 浏览器确认

1. 打开开发者工具 → Network。
2. 执行多源搜索、打开任务详情、封面和在线阅读。
3. Request URL 必须以当前页面 Origin 开头，例如 `http://192.168.1.10:3000/v1/...`。
4. 不应出现指向 `192.168.1.20:8080` 的浏览器请求，也不应依赖 `Access-Control-Allow-Origin`。
5. 搜索 POST、源站配置 PUT/DELETE、任务 SSE、图片/下载二进制响应均应保持原状态码、Content-Type 和响应体。

SSE 可用下列命令确认没有被缓冲：

```bash
curl -N http://192.168.1.10:3000/v1/tasks/events
```

### 5.3 项目回归检查

```powershell
node .\scripts\check_reverse_proxy_config.mjs
npm --prefix .\apps\web run test
npm --prefix .\apps\web run build
.\scripts\check.ps1
```

## 6. 常见问题排查

| 现象 | 优先检查 | 处理 |
|---|---|---|
| 502 / `backend API unavailable` | 前端设备能否访问后端 IP:8080；后端是否监听 `0.0.0.0`；防火墙规则 | 先直接访问后端 `/v1/sources`，再检查 `BACKEND_API_URL` |
| Next.js 返回 500 | Rewrite 连接失败、DNS 错误或 15 分钟超时 | 查看 Next.js 服务端日志；确认构建时变量并重建/重启 |
| `/v1/**` 404 | 后端 URL 错带 `/v1`、Nginx location 缺少尾斜杠、部署仍是旧构建 | `BACKEND_API_URL` 只填根地址；运行配置检查并重载 |
| 浏览器仍报 CORS | 浏览器仍在使用旧的绝对 API Base 或旧缓存 | Network 检查 Request URL；清理旧构建并重建，确认 `NEXT_PUBLIC_API_BASE` 编译为空 |
| 封面/阅读图片失败 | 后端设备自身拉图失败、响应 Content-Type 错误、网关超时或缓冲 | 直接访问同一 `/v1/` 图片 URL；检查服务端日志、900 秒超时和 `proxy_buffering off` |
| SSE 迟迟不更新 | 中间代理缓冲、连接超时、网关前还有 CDN | 保留 `proxy_buffering off` 与 `X-Accel-Buffering: no`，让 CDN 禁用该路径缓存 |
| 修改后端地址未生效 | Next Rewrite 已编译进旧构建 | 方案 A 重建并重启；方案 B 重新渲染配置并 `nginx -t` 后 reload |

## 7. 方案选择

| 方案 | 优点 | 缺点 | 推荐场景 |
|---|---|---|---|
| A：Next.js Rewrites | 文件少、零额外服务、本地体验完全兼容、所有 `/v1` 自动覆盖 | 代理故障只能得到 Next 内置 500；切换目标需重建/重启；TLS/限流能力有限 | 局域网、个人部署、前端保留 Node |
| B：Nginx 网关 | 标准 JSON 502、流式参数明确、TLS/日志/限流成熟、切换后端只需 reload | 多一个服务和模板渲染步骤 | 生产环境、公网入口、多设备长期运行 |
