# Fangliding 公开访问 403 诊断与匿名访问修正

> 日期：2026-07-29

> 2026-07-31 更正：Fangliding 公共页面正常情况下无需登录。此前根据一次临时 HTTP 403 增加浏览器会话配置入口，属于把网络/站点瞬时故障错误建模成认证能力。该入口已经移除；Fangliding 继续作为默认匿名来源参与搜索。

## 现象

最新搜索任务 `ca4797dc-c859-4bbe-b9b2-e662fa8ae158` 在 2026-07-29 22:53 完成：18comic 与 E-Hentai 正常返回并合并 65 条结果，Fangliding 单源失败。桥接错误为 `access_blocked`，目标地址是：

```text
https://ex.fangliding.eu.org/?f_search=female%3Afutanari&f_cats=0&page=0
```

前一天的同类三源任务仍能获得 90 条合并结果，因此这不是固定的查询映射或解析错误。

## 诊断结论

1. 从本机直接访问 Fangliding 首页返回 HTTP 403。
2. 直接访问同一搜索 URL 返回 HTTP 403。
3. 使用现代浏览器 User-Agent、`Sec-Fetch-*` 和 Client Hint 等完整导航请求头仍返回 HTTP 403。
4. 反向代理没有参与以上直接请求，因此本次阻断不是 Next.js Rewrite 造成的。
5. Fangliding 桥接器支持运维级 `FANGLIDING_COOKIE_FILE` 和 `FANGLIDING_HEADERS_FILE` 环境覆盖，但这不代表公共来源需要登录，也不应据此向普通用户展示认证面板。

公开检索信息仍指向同一个域名，没有发现可验证的新官方镜像域名；第三方状态检查对站点是否可用的结论不一致。项目不会猜测域名，也不会用 E-Hentai 的结果冒充 Fangliding。

## 项目修复

- Fangliding 适配器版本由 `0.4.1` 升级为 `0.4.2`。
- 从统一源站注册表删除错误的 `auth` 声明；`/v1/sources` 对 Fangliding 返回 `auth: null` 且 `available_for_default: true`，控制台不再显示会话配置入口。
- 保留桥接器现有 `FANGLIDING_COOKIE_FILE` 和 `FANGLIDING_HEADERS_FILE` 环境别名，仅供明确需要时由运维人员手工覆盖，不进入普通业务流程。
- 搜索页全部被拦截时保留 `HttpStatusError` 类型，桥接错误稳定输出 `access_blocked`，不再依赖错误文案中的关键词推断类型。
- 离线测试同时覆盖分页规则、匿名来源契约与阻断错误契约，并确认 18comic 的可选认证能力仍由通用机制承载。

## 使用方法

修改生效后需重新加载配置：

```powershell
cd "<项目目录>"
.\scripts\dev.ps1 -Fresh
```

然后直接选择 `Fangliding` 或“全部可用源站一起爬取”并搜索，不需要登录，也不需要填写 Cookie 或请求头。

如果普通浏览器和桥接器同时得到 403，则当前是站点端或网络侧访问限制。项目会继续保留其他来源结果并明确标记 Fangliding 暂时不可用，但不会把临时访问故障错误提示成“需要登录”，也不会破解验证码、绕过 Cloudflare、封禁或访问控制。
