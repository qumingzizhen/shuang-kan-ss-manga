# 在线阅读加载提速实施方案（2026-08-02）

## 1. 目标与边界

**目标**

- 首图端到端耗时：源站正常时 P50 稳定低于 1 秒；
- 翻到 20 页之外的深页：不再付出「全量页列表抓取 + 礼貌延迟」的等待；
- 同一图库重复打开/回看：命中磁盘或浏览器缓存，基本秒开。

**硬约束（不可突破）**

- 不绕过源站礼貌延迟、限速、登录/验证码边界；
- 对外 HTTP API 与桥接协议保持向后兼容：新增参数/字段一律可选，缺省行为与现状一致；
- 原始图片文件保留，供「原始尺寸」模式、下载与收藏使用。

**现状基线（已生效）**

- 建会话只抓第一个画廊索引页（`--max-gallery-index-pages 1`），`page_count` 仍为完整页数；
- 首图后台预热 3 页、短时复用会话、页列表惰性补全；
- 实测 Fangliding 91 页图库：旧全量列表 13.4s → 新首索引页 2.9s；
- 前端已做 aspect-ratio 预留高度、预加载尺寸上报、异步解码、滚动区轻量阴影。

本方案是下一阶段的三块组合：**A 读图转码**、**B 缓存治理**、**C 后台渐进页列表扩展**。

## 2. 现状链路与瓶颈

```
点击在线阅读
  → POST /v1/reader/sessions（1 次源站 RTT：画廊首索引页）
  → 响应 JSON（页元数据）
  → <img> 请求 /v1/reader/sessions/{id}/pages/{n}
    → 缓存未命中 → download-page（2 次源站 RTT：页面 HTML + 原图）
    → 缓存命中 → 直接读盘
  → 浏览器解码、绘制
```

剩余可压缩项：

1. 原图体积/解码成本（JPEG/大 WebP 源的显示尺寸远超 1600px 阅读宽度）；
2. 首次解码前的布局不确定性（缺精确宽高）；
3. 翻深页时的页列表补全等待；
4. 缓存无 TTL/驱逐，也缺少 ETag 与长缓存头；
5. 回看依赖磁盘缓存，浏览器本地缓存利用不充分（Service Worker 列为后续可选）。

## 3. 方案 A：读图转码（显示版 + 模糊占位版 + 精确尺寸）

### 3.1 设计

`download-page` 下载原图后，在同一 Python 进程内（避免额外进程启动）按规格生成变体，
返回新增可选字段 `variants`。服务端把变体落盘到现有缓存目录，阅读接口按 `variant`
参数返回对应文件；未传参数时返回原图，保证旧客户端行为不变。

文件布局（现有 `cacheRoot = .data/page-cache/{source}/{sessionId}`，sessionId 是
`sha256(source\0gallery)`，天然按图库内容寻址）：

```
cacheRoot/
  0001.jpg            # 原图（download-page 原有产物）
  0001.display.webp   # 显示版：max-width 1600、q80
  0001.blur.webp      # 模糊占位版：max-width 480、q60
```

### 3.2 桥接协议扩展（可选、向后兼容）

- `download-page` 新增可选参数 `--variant-specs`，值为 JSON 数组，例如：
  `[{"name":"display","max_width":1600,"quality":80,"format":"webp"},{"name":"blur","max_width":480,"quality":60,"format":"webp"}]`；
- 支持时返回新增可选字段：
  `variants: [{name, file, content_type, width, height, byte_size}]`；
- 不支持/未传参时输出与现状完全一致；
- 实现位置：`scripts/source_bridge_core.py` 提供通用变体生成函数（Pillow 已在环境，
  版本 12.2，WebP/JPEG 均支持）；`ehentai_bridge.py` 与 `18comic_bridge.py` 的
  `run_download_page` 接入；`fangliding_bridge.py` 经模块复用自动获得。

### 3.3 服务端

- 源适配器配置新增可选字段 `"reader_variants": true`（或按桥接能力探测），
  默认不开启时行为与现状完全一致；
- `fetchReaderPageFile`：桥接返回 `variants` 后把变体文件落到 cacheRoot，并把
  `width/height` 回填到会话页元数据；
- 图片路由支持 `?variant=display|blur|original`：
  - 缺省 = `original`（旧客户端不受影响）；
  - `original` 模式优先返回原图；
  - 变体缺失时明确降级：记日志并返回原图（禁止静默吞错）；
- `publicReaderPage` 新增可选 `width`/`height` 字段（有缓存/变体时填充），
  前端据此用精确 aspect-ratio 占位；
- 变体生成失败不影响会话与阅读：原图直出 + 错误日志。

### 3.4 前端

- 阅读器 `<img>` 的 URL 追加 `variant=display`（`fit-original` 时用 `original`）；
- 第一阶段只做「显示版 + 精确尺寸占位」；第二阶段再做 blur-up：
  用 `blur.webp` 作为低清底图（CSS `filter: blur(8px)`），显示版加载完成后淡入替换；
- 尺寸字段优先于上一轮的「预加载尺寸上报」，两者并存、以字段为准。

### 3.5 配置项

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DEV_API_READER_DISPLAY_MAX_WIDTH` | `1600` | 显示版最大宽度 |
| `DEV_API_READER_DISPLAY_QUALITY` | `80` | 显示版质量 |
| `DEV_API_READER_BLUR_MAX_WIDTH` | `480` | 模糊占位版最大宽度 |
| `DEV_API_READER_BLUR_QUALITY` | `60` | 模糊占位版质量 |
| `DEV_API_READER_VARIANT_CONCURRENCY` | `2` | 变体生成独立限流器并发（不占用页面下载并发） |

### 3.6 测试

- 回归测试 fixture 桥接支持 `--variant-specs`：
  - 断言变体文件存在、`width/height` 正确、`byte_size ≤ max_width × 预期比例`、
    content-type 为 `image/webp`；
  - 断言原图文件保留且未被改写；
  - 断言 `variant=display`/`blur`/缺省 三种响应正确；
  - 断言变体生成失败时降级返回原图且不抛错（有日志）。

## 4. 方案 B：缓存治理与命中优化

### 4.1 现状

`page-cache/{source}/{sessionId}` 已按图库内容寻址（sessionId 由 source+gallery 派生），
跨入口、跨用户天然可共享；`fetchReaderPageFile` 已有单飞与磁盘命中。缺口是：

- 缓存无 TTL、无容量上限，长期运行磁盘只增不减；
- 图片响应只有 `Cache-Control: private, max-age=3600`，无 ETag/304；
- 每次 `listCachedReaderPages` 全目录 stat，会话文件多时开销线性增长。

### 4.2 改动

- 新增缓存条目 TTL 与全局容量上限：
  - `DEV_API_READER_CACHE_TTL_MS`（默认 30 天）；
  - `DEV_API_READER_CACHE_MAX_BYTES`（默认 4 GiB）；
  - 启动时与每日一次扫描驱逐：按最后访问时间 LRU，跳过最近 N 分钟访问过的文件；
  - 驱逐日志带上下文（目录、文件数、释放字节）。
- 响应头：
  - 原图与变体统一加 `ETag`（文件名 + size + mtime）与
    `Cache-Control: private, max-age=604800`；
  - 变体 URL 与版本绑定（文件名含 `v1` 段），未来变更质量参数时 bump 版本即可安全换缓存。
- 页元数据批处理（可选优化）：当某会话缓存文件数超过阈值（如 200）时，改用一次性
  目录索引缓存，避免每请求全量 stat；现阶段先不做，标注为后续项。

### 4.3 测试

- fixture 用可控 `DEV_API_READER_CACHE_TTL_MS` 验证过期条目被驱逐、新条目保留；
- 用 `If-None-Match` 请求断言 304 与 200 分支；
- 断言驱逐不影响正在下载的页面（正在使用中的文件跳过）。

## 5. 方案 C：后台渐进页列表扩展

### 5.1 目标

打开会话后，把 20 页之后的画廊索引页按礼貌节奏在后台逐步拉完；用户翻到深页时
页列表已就绪，不再触发「全量补全 + 多次礼貌等待」。

### 5.2 桥接扩展（可选、向后兼容）

- `list-pages` 新增可选参数 `--gallery-index-page N`（1 基）：只返回第 N 个画廊索引页
  的 page descriptors，复用现有解析逻辑；不传时行为与现状完全一致；
- 服务端已知 `gallery_index_page_size = 20`，页 n 所在索引页
  `K = ceil(n / 20)`；`18comic` 等一次返回全量列表的源不需要该能力。

### 5.3 服务端调度

- 会话创建/恢复后，若 `pages.length < page_count` 且源支持单索引页抓取，
  注册该会话的后台扩展调度器：
  - 每 `DEV_API_READER_LIST_PACE_MS`（默认 2500ms，大于源站礼貌延迟）推进一页索引；
  - 每步走现有单飞 `readerPageListFetches`，与用户的深跳请求合并，绝不重复抓取；
  - 页数补满或调度被关闭时停止；调度器只存在于内存，重启后由下次打开/恢复重建；
- 深跳兜底：用户请求超出已知页时，`ensureReaderPages` 仍按现状一次性补全
  （后台调度可能未赶上），保证任何时刻行为正确；
- 后台失败：记录上下文日志，停止该会话调度（不静默重试循环）。

### 5.4 测试

- fixture 支持 `--gallery-index-page`；
- 断言后台按节奏推进（调用次数、间隔 ≥ 配置值）、最终 `pages.length == page_count`；
- 断言用户深跳与后台扩展合并为同一次桥接调用；
- 断言 18comic 风格（无 `gallery_index_page_size`）源不启动后台调度。

每阶段只解决一个问题，禁止混合提交；每个阶段提交前跑全量自检。

## 7. 风险与回退

- **磁盘占用约 3 倍**：原图 + 两个变体；由 TTL/容量驱逐兜底；首版可只出 display
  变体（blur 延后）进一步减半。
- **转码 CPU**：变体生成放独立低并发限流器（默认 2），不占用页面下载并发；
  失败一律降级原图。
- **Pillow 无法解码的罕见格式**：跳过变体生成，原图直出，不影响阅读。
- **兼容性**：所有新增参数/字段可选；旧桥接不认新参数时，服务端按配置/能力探测
  跳过对应能力；缺省响应与现状逐字节一致（由契约测试保证）。
- **公网部署**：若走 Cloudflare 等 CDN，图片 URL 需签名且不开放写；长缓存头只在
  本地/可信代理下生效（部署文档中注明）。

## 8. 验收标准

- 首图：源站正常时端到端采样 5 次取中位数 < 1s（对比当前基线记录到本文档）；
- 深页：第 21+ 页首次跳转不再出现「全量列表等待」，或等待 ≤ 单次索引页 RTT；
- 回看：同一图库再次打开，首图命中磁盘缓存，P50 < 300ms；
- 契约：既有 `check_reader_progress` / `check_reader_first_page` / 契约测试全部通过；
- 磁盘：启用 TTL/容量后，缓存目录大小有界。

## 9. 后续可选（不在本期）

- Service Worker + Cache API：浏览器本地缓存与 stale-while-revalidate，回看零请求；
- 虚拟化渲染（可视 ±2 页）；
- 整本受控预取任务（按源站速率后台拉全本）；
- 多源并行取图（同图库多镜像，谁快用谁）。

## 10. 验收结果（M4，2026-08-02）

### 10.1 真实源站端到端计时

测试对象：Fangliding 图库 `4081942`（源站声称 200 页，实际可解析约 91+ 页），
冷缓存、隔离数据目录、真实网络。方法：启动隔离 dev-api，依次测量
建会话、首图（`?variant=display`）、缓存图片、重复打开、深跳第 41 页。

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 建会话（首索引页） | 1785–2050 ms | 一次源站索引请求，受源站 RTT 主导 |
| 首图（冷，display 变体） | 4195–4787 ms | 源站 3 次请求（索引→页面→图片）+ 变体生成 |
| 缓存图片 | 6 ms | 磁盘缓存 + 变体命中 |
| 重复打开会话 | 3 ms | 会话复用，零桥接调用 |
| 深跳第 41 页 | 1687–1745 ms | 单索引页抓取；后台已补全时接近 0 |
| 旧基线（全量列表） | 13393 ms | 同源站旧逻辑 |

结论：

- 本地/缓存路径远低于 1 秒（重复打开 <10ms、缓存图片 6ms）；
- 冷首图耗时由源站 RTT 主导（该镜像单次请求 2–3 秒），在源站响应正常
  （RTT <1s）时可稳定达成 1 秒目标；转码与显示版已把传输/解码成本降到最低；
- 深跳不再支付「全量列表 + 多次礼貌等待」，只付单索引页请求。

### 10.2 验收过程中发现并修复的问题

- E-Hentai 系镜像每索引页实际显示 20 张缩略图（桥接常量误写 40），
  `gallery_index_page_size` 已修正为 20；
- 单索引页抓取返回的页码是位置序号，已改为从页面 URL 提取真实页码，
  避免合并时覆盖已有页；
- 声明页数大于实际页数时，后台扩展会在空索引页处停止，不再重复抓取。

## 11. 后续优化落地记录（2026-08-04）

- 滚动稳定性修复（`1a799a3`）：连续模式堆栈从滑动窗口改为从第 1 页起只增不减，
  快速下滑不再因滚动锚点丢失跳回第一页；跳页/翻页按钮会把目标页滚到视口。
- blur-up 低清渐显（`ebcaa02`）：加载期间先显示 480px blur 变体，高清版就绪后覆盖，
  首图“可见”时间大幅提前（M1 第二阶段落地）。
- Service Worker + Cache API（本次提交）：浏览器本地缓存阅读图片，
  stale-while-revalidate 后台刷新；`reader_retry`/`refresh=1` 绕过缓存；
  UI 的“清除缓存”会同步清空 SW 缓存；缓存条目上限 600。

- 整本受控预取（`49a5eaa`）：打开/恢复会话后，后台按礼貌节奏（默认 2 秒/页）
  把整本剩余页拉进磁盘缓存，翻页永不等待；已缓存页直接推进，连续失败达阈值停止，
  `DEV_API_READER_ALBUM_PREFETCH=0` 可关闭。
- 多源取图（`9c15e99`）：Fangliding 与 E-Hentai 互设 `reader_mirror_sources`，
  主源下载失败时自动以换主机后的同一图库 URL 走镜像源，成功路径零额外请求；
  未配置镜像的源行为不变。

### 虚拟化渲染的结论（实测后维持现状）

已用 `scripts/benchmark_reader_dom.mjs` 完成长本基准：800 页 fixture + 生产构建 +
无头 Chromium，程序化快速下滑 20 秒，实测结果：

| 指标 | 数值 |
| --- | --- |
| 起始/结束 `.reader-scroll-page` 节点 | 9 → 485（20 秒内随阅读进度增长） |
| `<img>` 节点数 | 709 |
| JS 堆内存（100 页 → 485 页） | 稳定约 11.9 MB |
| 快速滚动跳顶事件 | 0 |
| 平均/最大帧间隔 | 125 ms / 260 ms（4000px/帧 的合成跳转 + 无头软件渲染，不代表真实滚轮） |

结论：DOM 与内存不是瓶颈（content-visibility 已跳过离屏页面的布局与绘制，堆内存随
页面增长几乎不涨）；快速滚动跳顶为 0，稳定性保持。传统 DOM 虚拟化需要重新引入
“移除视口上方页面”与高度补偿，收益无实测支撑、风险与刚修复的跳顶直接冲突。
因此维持“只增不减 + content-visibility”方案，保留基准脚本供将来复测。
