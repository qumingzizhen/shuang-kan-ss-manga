# 抽象复用问题整改与验收报告（2026-07-29）

## 1. 本轮目标与结论

本轮针对《代码结构与可复用性审查》中发现的高优先级问题进行工程化整改。改动遵循以下边界：保留原有启动入口、HTTP 路径、请求字段、任务模型和返回结构；不新增与业务无关的依赖；不安装系统组件、不修改系统服务、不触发重启。

本轮完成后，源站能力、任务仓储、任务队列、Worker 重试、Python 桥接、结构化错误、多源搜索合并和来源认证均有明确的可替换边界。Fangliding 不再依赖项目目录外的旧下载器，也不再通过运行时猴子补丁覆盖下载逻辑。

## 2. 问题与整改映射

| 原问题 | 代码整改 | 设计依据 | 兼容性 |
|---|---|---|---|
| 源站能力只有少量枚举，阅读能力靠调用方猜测 | `packages/domain/src/lib.rs` 补齐 `gallery`、`download`、`retry_folder`、`page_list`、`page_image`、`online_read`；注册表集中校验 | 能力声明属于领域契约，调用方只依赖能力，不依赖站点名称 | 原字段与接口保留，仅增加可识别能力 |
| API 与独立 Worker 使用内存队列，跨进程任务不可见 | `packages/task-queue/src/postgres.rs` 增加 PostgreSQL 队列，支持租约、确认、延迟重试与消费者标识 | 队列传输应位于 `TaskQueue` 抽象之后 | 本地默认仍为 `memory`；生产可显式选择 `postgres` |
| 任务仓储是具体实现枚举，新增存储需要改调用方 | `services/api/src/repository.rs` 引入对象安全 `TaskStore`，`TaskRepository` 作为稳定门面 | 依赖倒置，业务层只依赖仓储行为 | `TaskRepository::from_env/insert/update/get/list` 全部保留 |
| Worker 只记录日志，无法把独立进程结果写回任务 | `workers/download/src/reporter.rs` 增加 PostgreSQL Reporter | 执行器与状态持久化通过 `TaskReporter` 解耦 | 内存模式继续使用追踪 Reporter |
| Python 各来源重复实现 HTTP、图片校验、原子写入和下载调度 | `scripts/source_bridge_core.py` 提供共享客户端、重试、图片验证、原子保存和有界并发下载工作流 | 模板方法：公共机制集中，来源脚本只保留 URL 与解析规则 | 命令行入参与 JSON 输出不变 |
| Fangliding 依赖项目外脚本并以猴子补丁修正下载 | `scripts/fangliding_bridge.py` 变为 E-Hentai 兼容核心的薄配置层；`scripts/ehentai_bridge.py` 参数化来源标识 | 同协议站点使用同一实现，差异通过配置注入 | Fangliding 的标准 bridge 命令、环境变量前缀和输出结构不变 |
| Rust、Node、Python 的桥接错误格式没有单一契约 | `BridgeErrorPayload`、`bridge-error.schema.json`、`bridge-protocol.mjs` 与 Python 输出共享字段 | 契约优先，拒绝未知字段，便于跨进程重试 | 仍使用既有 stderr 前缀；错误字段增加明确语义 |
| Node 合并结果逐项线性扫描，结果多时退化为 O(n²) | `services/dev-api/search-results.mjs` 使用精确标题索引与 bigram 倒排候选集 | 先缩小候选集，再做相似度判定 | 去重、元数据合并和全来源时间排序语义不变 |
| Rust 搜索合并与开发 API 行为不一致 | `packages/task-runtime/src/search_merge.rs` 实现 URL/标题归一化、跨来源软去重和全局时间排序 | 两条后端链路共享同一领域语义 | 任务输出结构不变 |
| Node 服务和 Dashboard 内嵌来源认证逻辑 | `services/dev-api/source-auth.mjs` 与 `apps/web/src/components/source-auth-panel.tsx` 分离状态、文件写入和 UI | 高内聚：认证管理可独立测试与替换 | HTTP 路由、请求体和界面入口保留 |

## 3. 关键链路

### 3.1 本地模式

```text
API 创建任务
  -> TaskRepository(memory)
  -> TaskQueue(memory)
  -> API 进程内 WorkerRuntime
  -> TaskDispatcher
  -> SourceAdapter
```

### 3.2 跨进程模式

```text
API 创建任务
  -> TaskRepository(postgres)
  -> TaskQueue(postgres)
  -> 独立 download worker 租约消费
  -> TaskDispatcher
  -> SourceAdapter
  -> PostgresTaskReporter 更新任务状态
  -> ack / retry
```

当 `TASK_QUEUE_BACKEND=postgres` 时，API 会强制要求 `TASK_REPOSITORY=postgres`，避免“消息已被独立 Worker 消费但任务状态仍留在另一个进程内存中”的不一致。

### 3.3 E-Hentai 兼容来源

```text
config/source-adapters.json
  -> scripts/fangliding_bridge.py（仅注入来源配置）
  -> scripts/ehentai_bridge.py（搜索、详情、阅读、下载命令）
  -> gallery_search_parser.py（结果解析）
  -> source_bridge_core.py（HTTP、重试、校验、原子写入、调度）
```

## 4. 扩展成本量化

新增一个“标准 E-Hentai 兼容来源”的最小路径：

1. 新增一个约 35～55 行的薄包装脚本，仅声明 `SOURCE_ID`、名称、主页和环境变量别名；
2. 在 `config/source-adapters.json` 新增一条约 25～40 行的描述与注册配置；
3. 新增 1 个约 30～60 行的离线夹具测试，或在现有参数化测试中增加一组数据。

因此最少改动 **3 个文件、约 90～155 行**；Rust API、任务调度、下载 Worker、开发 API 路由和前端无需修改。对于非兼容站点，仍需编写站点专用 URL/解析规则，但 HTTP、重试、图片写入、并发下载、错误协议、搜索合并与界面链路均可复用。

新增一种任务仓储或队列实现时，通过实现 `TaskStore` 或 `TaskQueue` 并在组合根注册完成；业务路由与 WorkerRuntime 不需要修改。新增一种下载重试策略时应扩展策略对象或错误重试元数据，不应把来源判断写进运行时。

## 5. 性能与健壮性

- 多源软去重由对全部已有结果逐项扫描，改为精确索引和 bigram 倒排候选集；1200 条合成结果的最终本地基线为 44.50 ms（阈值 2500 ms）。
- 图片先写 `.part` 临时文件，验证成功后再原子替换，避免留下看似成功的截断文件。
- PostgreSQL 队列通过租约避免 Worker 崩溃后消息永久丢失，租约到期可由其他消费者重新领取。
- 错误契约包含 `code`、`retryable`、`retry_after_ms` 和 `source_id`，Worker 只重试明确可重试错误并限制最大次数。
- 来源认证文件使用临时文件加原子替换，避免进程中断时写出半截 JSON。

## 6. 配置与运行

本地启动方式没有变化：

```powershell
.\scripts\dev.ps1 -Fresh
```

本地开发默认使用：

```dotenv
TASK_REPOSITORY=memory
TASK_QUEUE_BACKEND=memory
```

跨进程部署时使用：

```dotenv
TASK_REPOSITORY=postgres
TASK_QUEUE_BACKEND=postgres
API_LOCAL_WORKER=false
DATABASE_URL=postgres://...
WORKER_MAX_ATTEMPTS=3
```

队列连接数、轮询间隔、租约时间和消费者标识见 `.env.example`。Cookie、请求头和本地认证仍保存于被 Git 忽略的 `.data` 目录。

## 8. 后续边界

- NATS 可作为未来传输实现，但不是当前必需依赖；当前 PostgreSQL 队列已经覆盖 API 与 Worker 跨进程共享。
- 本地文件库的 CBZ/PDF/目录读取仍应继续向格式 Provider 注册表演进，该项涉及文件库业务模型，需独立变更并配套迁移测试，不应混入本轮源站与任务执行重构。
